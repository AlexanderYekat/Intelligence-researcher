# Дорожная карта

Это дорожная карта **разработки самого оркестратора**, а не план уже выполняемого автономного исследования. Упомянутые ниже research goal и workflow — тестовые входные данные, на которых будет проверяться создаваемый инструмент.

Цель roadmap — сначала построить работающий вертикальный прототип, не превращая подготовительный этап в строительство универсальной инфраструктуры.

## Этап 0 — Концепция и контракты

Результат:

- словарь сущностей;
- task schema;
- artifact schema;
- adapter contract;
- state machine;
- критерии MVP;
- описание одного небольшого демонстрационного research goal как тестового сценария, без запуска большого исследования.

Критерий выхода: два человека или агента одинаково понимают жизненный цикл задачи и формат результата.

## Этап 1 — Создать минимальный вертикальный прототип

Нужно реализовать один процесс и один тестовый проект, способные:

1. принять тестовый goal из CLI;
2. загрузить заранее подготовленный небольшой DAG;
3. запустить два разных worker-адаптера;
4. собрать artifacts;
5. выполнить schema/deterministic review;
6. запросить LLM review;
7. сохранить accepted result в Git;
8. показать статус.

На этом этапе исследование служит испытательным стендом. Цель этапа — создать и проверить инструмент, а не получить полноценный предметный research-результат.

Критерий выхода: end-to-end demo повторяется на чистой машине по инструкции.

## Этап 2 — Research Program

Добавить:

- генерацию RQ и workstreams;
- investigations и synthesis checkpoints;
- версионирование program plan;
- templates findings/decisions;
- replan после synthesis;
- вложенную декомпозицию слишком большой задачи.

Критерий выхода: система проводит минимум два цикла исследования и второй цикл реально зависит от первого.

## Этап 3 — Model Router и review

Добавить:

- capability profiles;
- tier policies;
- историю успехов по классам задач;
- automatic escalation;
- independent/adversarial review;
- бюджеты attempts.

Критерий выхода: слабый результат дешёвой модели отклоняется и корректно эскалируется без ручного переноса контекста.

## Этап 4 — Durable execution

Добавить:

- PostgreSQL state store;
- leases и heartbeat;
- durable timers;
- idempotency keys;
- recovery после kill/restart;
- watchdog;
- worktree lifecycle.

Критерий выхода: во время активной задачи процесс принудительно завершается, затем система автоматически восстанавливается без потери принятого состояния.

## Этап 5 — Quota Broker

Добавить:

- quota pools;
- ручные и автоматические observations;
- quota errors и `available_at`;
- reservations;
- продолжение других задач во время wait;
- прогноз расхода;
- quota harvesting с safety policy.

Критерий выхода: демонстрационный workflow переживает искусственный лимит, использует альтернативного worker и продолжает исходную задачу после reset.

## Этап 6 — Масштабирование

Только после подтверждения MVP:

- несколько машин/worker pools;
- Temporal, если собственный runtime стал дорогим;
- object storage;
- web dashboard;
- multi-project fairness;
- plugin/skill registry;
- benchmark-driven routing;
- уведомления и human approval UI.

## Предлагаемый первый кейс

Практичный dogfooding-сценарий:

> Исследовать инструменты для статического анализа 1С 7.7 и определить минимальную архитектуру semantic layer.

Почему он подходит:

- есть несколько репозиториев-кандидатов;
- нужны и статический обзор, и эксперименты;
- работа естественно делится на workstreams;
- выводы требуют synthesis;
- часть задач массовая, часть архитектурно сложная;
- результат полезен независимо от успеха самого оркестратора.

## MVP считается завершённым, если

- goal, DAG и artifacts имеют стабильные схемы;
- минимум два provider/CLI adapters работают через общий контракт;
- есть review и один сценарий escalation;
- есть Git-backed memory;
- есть восстановление после сбоя;
- есть quota wait/resume;
- каждое решение scheduler объяснимо в журнале;
- документация честно перечисляет ограничения.

## Что пока не строить

- Kubernetes-кластер;
- marketplace агентов;
- сложную графовую БД;
- универсальный визуальный редактор DAG;
- самоизменяющееся ядро;
- десятки provider adapters;
- полностью автоматический production deployment.

Эти вещи могут понадобиться, но не подтверждают главную гипотезу: способен ли оркестратор надёжно превращать большую цель в накопление проверяемого знания и принятых результатов.
